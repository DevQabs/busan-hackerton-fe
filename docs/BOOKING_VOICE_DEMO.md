# 배차 예약 — 페이지 설명 · 시연 준비

<!-- 반영·검증: 2026-07-26 · [BookingApp.tsx](../components/booking/BookingApp.tsx) · [PlaceInput.tsx](../components/booking/PlaceInput.tsx) · [voice.ts](../lib/voice.ts) -->

내비게이션 밖 독립 라우트 `/booking`. 질문: **지금 부를까, 그리고 거기 가면 쓸 수
있나.** 대시보드가 도시 단위 진단이라면 이 페이지는 한 사람의 한 번의 이동이다.

같은 화면이 두 모드로 갈린다. 일반 모드는 눈으로 쓰고, **음성 모드(`?voice=1`)는
화면을 전혀 보지 않고 완주한다.** 설계 근거는
[.omc/specs/deep-interview-booking-voice-scope.md](../.omc/specs/deep-interview-booking-voice-scope.md).

## 데이터

`dongs.geojson`(경계·centroid, 206 동) · `dispatch_eta.json`(동×시각 대기 셀) ·
`infra_points.json`(충전소·복지·관광·병의원, 시 전역) ·
`haeundae_facilities.json`(화장실·주차장·승강기, 해운대구만) ·
`access_actions.json`(무장애가게 12항목 실사, 321곳).

장소 검색과 경로는 `app/api/places` · `app/api/directions` 무상태 프록시를 지난다.
카카오 REST 키를 브라우저에 노출하지 않기 위한 것이고 **여기에 상태는 없다** —
AGENTS.md의 no-backend 규칙은 유지된다.

`travel_times.json`을 쓰지 않는다. 대기시간은 출발지 동×시각의 관측 중앙값이고
경로는 카카오모빌리티 응답을 그대로 그린다.

## 계산

```
대기      = lookupWait(출발 좌표 → 행정동, 시각)   dispatch_eta 셀의 minutes
보정      = minutes × CHAIR_WAIT[chair]            none 1 · 수동 1.08 · 전동 1.18
시설      = nearestByKind(도착 좌표, 반경 5km)     6종 각 최근접 1곳, 없으면 배열에서 빠짐
무장애가게 = groupNearbyShops(도착 좌표, 반경 1.5km, 칸당 5곳)
```

출발지가 행정동 경계 밖이면 가장 가까운 centroid로 떨어지고(15km 넘으면 포기),
해당 시각 셀이 없으면 그 동의 중위 시간대 값을 쓴다. 둘 다 화면에 각주로 붙는다.

**`chair` 기본값은 `none`이다.** 음성 흐름의 사용자는 시각장애인이고 거기에 휠체어를
겹치면 페르소나가 흐려진다. 부수 효과가 하나 있는데 의도한 것이다 —
`wheelchairFit`은 `none`이면 판정을 건너뛰고 전부 `fit`으로 돌려주므로
(`lib/wheelchair.ts:73`), 그 상태에서 "이용 가능 5곳, 확인 필요 0곳"이라 말하면
**하지도 않은 검사를 발견인 것처럼** 제시하게 된다. 그래서 `none`일 때 낭독은 판정
표현을 쓰지 않고 개수만 말한다.

## 두 모드

| | 일반 `/booking` | 음성 `/booking?voice=1` |
|---|---|---|
| 입력 | 타이핑 검색 · 슬라이더 | **화면 전체가 탭 면** |
| 마이크 버튼 | **없다** | 필드마다 노출(탭 면 아래라 시각 신호용) |
| 업종 칩·스크롤·지도 | 전부 정상 | 탭 면에 덮여 조작 불가 |
| 나가기 | — | 우상단 56px `끄기` |

모드 진입은 URL이거나 헤더의 🎤 버튼이다. **자동 감지는 불가능하다** — 브라우저는
스크린리더가 켜져 있는지, 사용자가 시각장애인인지 알 방법이 없다.

음성 모드에서 제스처는 **두 개뿐**이다. 눈 없이 구별할 수 있는 최소 집합이고,
스와이프·더블탭·두 손가락은 무대에서 실패한다.

| 제스처 | 동작 |
|---|---|
| 짧게 탭 | 다음 단계. 3개가 다 차면 결과 다시 듣기 |
| 길게 누르기 600ms | 직전 단계를 다시 말한다 |

큰 버튼 하나로는 안 된다. 화면을 못 보는 사람에게 그 버튼이 **어디 있는지**가 이미
모르는 정보이기 때문이다. 탭 면은 투명하다 — 소리는 조작하는 사람의 것이지만 화면은
심사위원의 것이라, 덮어버리면 "소리가 진짜였다"는 증거가 사라진다.

## 낭독 문장

세 입력이 다 차면 아래 7절을 이 순서로 이어 한 문장열로 읽는다(`composeAnswer`).
`SpeechSynthesis`, `lang="ko-KR"`, rate 1.15, 약 30초.

| # | 절 | 조건 |
|---|---|---|
| 1 | `{출발지}에서 {도착지}로 {H}시 출발입니다.` | 복창 — 오인식을 여기서 잡는다 |
| 2 | `예상 대기시간은 약 {N}분입니다.` | wait 있음 |
| 3 | `{동} {H}시 접수 기준이고, 미배차와 취소 가능성은 {P}퍼센트입니다.` | wait 있음 |
| 4 | `도착지 주변 접근시설은 {종류} {이름} {거리}, …입니다.` | 상위 3개 |
| 5 | `다른 종류 시설 {M}곳이 더 있습니다.` | M > 0 |
| 6 | `도착지 주변 무장애가게는 {K}곳입니다.` | `chair=none` |
| 7 | `가장 가까운 곳은 {이름}, {거리}입니다.` | K > 0 |

같은 문자열이 세 곳으로 나간다: 앱 TTS · `aria-live="polite"` · 화면 텍스트.
하나의 변수에서 갈라지므로 셋이 어긋날 수 없다.

**낭독에서 뺀 것** — 95% 신뢰구간 · 표본 수 · `hourFallback`/`exactDong` 각주 ·
`meta.caveats` · 반경 안에 **없는** 시설 종류 · 경로 거리와 차량 소요 · 지도 ·
12항목 태그 · 업종 칩.

버린 게 아니라 **채널을 나눈 것**이다. 심사위원은 화면을 눈으로 읽고, 귀로 듣는
사람에게 그 값들은 행동을 바꾸지 않는다. 반대로 **미배차·취소 비율은 넣었다** —
"차가 아예 안 올 수도 있다"는 통계가 아니라 지금 나갈지 말지를 바꾸는 정보다.

표기는 화면과 다르다. `%`→`퍼센트`, `m`→`미터`, `km`→`킬로미터`. TTS 엔진에 따라
`m`을 영문자로 읽는다.

## 입력 중 소리

| 사건 | 소리 | 화면 |
|---|---|---|
| 마이크 열기 전 | `{라벨}, 말씀하세요.` | ○ |
| 검색 중 | **✕** | ○ |
| 출발지 확정 | `출발지, {이름}. 도착지 입력을 위해 터치해 주세요.` | ○ |
| 도착지 확정 | `도착지, {이름}. 탑승 시각 입력을 위해 터치해 주세요.` | ○ |
| 탑승 시각 확정 | `탑승 시각, {H}시` → 1.8초 뒤 전체 낭독 | ○ |

**안내를 다 말한 뒤에 마이크를 연다.** 동시에 열면 마이크가 자기 TTS를 되받아
"출발지 말씀하세요"를 장소 이름으로 인식한다. 낭독이 불가능한 기기에서도 마이크는
열리도록 `onEnd` 미도착 대비 타임아웃을 둔다.

"검색 중"만 소리에서 뺐다. 카카오 검색이 300~600ms라 그 문장(1.2초)을 말하는 동안
결과가 도착해 확정 복창과 겹친다 — 소리가 소리를 방해하는 유일한 지점이다.

확정 복창이 다음 단계를 함께 말하는 것은 흐름 때문이다. "출발지, 센텀삼익아파트"만
들려주고 끝내면 화면을 못 보는 사람은 거기서 멈춘다. 손으로 목록을 클릭해 고른
경우에는 이 안내가 나가지 않는다.

## 무음 3초 → 3회째에 멈춤

| 회차 | 낭독 | 마이크 |
|---|---|---|
| 1·2회 | `잘 못 들었습니다. 다시 말씀해 주세요.` | 다시 열림 |
| 3회 | `소리가 들리지 않았습니다. 새로고침 후 다시 말씀해 주세요.` | 멈춤 |

인식이 성공하면 카운터는 0으로 돌아간다. 인식기의 `no-speech`에 맡기지 않는다 —
발화 시점 판정이 플랫폼마다 다르고 안드로이드에서는 아예 오지 않기도 해서 마이크가
열린 채 무한정 기다린다. 네이티브 `no-speech`와 자체 타이머가 함께 터져도 한 번으로
접는다.

**"오류"라는 말은 쓰지 않는다.** 화면을 보지 않는 사람에게 오류는 정보가 아니라
막다른 길이다. 무엇을 하면 되는지만 말한다.

## 시연 대본

전체 예산 90초(soft), 낭독 1회 35초. 아래는 실측 약 75초.

**시작 전(타이머 밖)** — 갤럭시 S26 Ultra + Chrome으로 `…/booking?voice=1` 열기 ·
마이크 권한 미리 허용 · 미디어 볼륨 최대, 무음 해제 · 화면 밝기 최대 ·
**TalkBack 끄기**(켜져 있으면 마이크가 TalkBack 낭독을 되받는다). 백업은 맥북 Chrome
같은 URL.

|---|---|
| 장소가 잘못 잡혔다 | **길게 누르기** → 그 단계를 다시 말한다 |

| 🔊 "인식 서버에 연결하지 못했습니다" | 홀 네트워크 문제. `끄기` → 일반 모드에서 손으로 입력해 같은 결과를 보여준다 |

| 완전히 꼬였다 | `끄기` → 일반 `/booking`. 모든 기능이 살아 있다 |

## 소리 내어 말할 단서

- 대기시간은 실시간 예측이 아니라 그 동×시각의 관측 중앙값이다.
- 100% 확정이 아니라 "약 46분" — 통계적 기대값이라는 뜻을 한 글자로 담았다.
- 화면의 숫자를 다 읽지 않는 것은 의도다. CI·표본은 화면에 있고 심사위원은 눈으로
  읽는다. 미배차 비율만 낭독에 넣은 것은 그것이 행동을 바꾸기 때문이다.
- `chair=none`이라 휠체어 판정을 하지 않았고, 그래서 "이용 가능 N곳"이라 말하지
  않는다. 휠체어를 고르면 판정이 켜지고 낭독도 바뀐다.
- 화장실·주차장은 해운대구 실사 데이터뿐이라 구 밖에서는 실제보다 멀게 나온다.
- `SpeechRecognition`은 오디오를 서버로 보낸다. 네트워크가 끊기면 인식이 실패한다.
- 앱이 직접 말하는 것은 실무 정답이 아니다 — 표준은 스크린리더 낭독이다. 일반인
  발표자와 무대 제약 때문에 TTS를 주경로로 두고, `aria-live`를 함께 갖춰 자기
  스크린리더를 쓰는 사용자는 앱 음성을 끄고 자기 속도로 들을 수 있게 했다.

## 남은 것

- **기기 실측 3종이 아직 없다.** 갤럭시 TalkBack 실기 완주 · 맥북 Chrome axe 위반
  0건 · 키보드만으로 완주. 심사위원이 "진짜 접근성이 있냐"고 물었을 때의 답이라
  가장 먼저 돌려야 한다.
- 안드로이드 Chrome이 인식 시작 시 자체 효과음을 낸다. 충분히 크면
  `"…말씀하세요"`가 중복이다 — 겹치면 `prompt` 문구를 비운다.
- 무음 회차당 5초(무음 3초 + 재시도 안내 2초). 3회면 15초라 90초 예산에서 크다.
  길면 재시도 문구를 "다시 말씀해 주세요"로 줄인다.
- `eslint`가 설치돼 있지 않아 `next build`가 린트를 건너뛴다. axe는 별도로 브라우저에서 잰다.
- 갤럭시 화면을 무대 스크린에 올리는 방법과 TTS를 장내 스피커로 보내는 경로가 미정.
- 음성 모드 진입은 수동이다. 실제 시각장애인이 `/booking`에 그냥 오면 일반 모드이고,
  거기엔 마이크가 없다 — 링크를 받거나 헤더 🎤를 찾아야 한다.
